# Влияние Race Condition на производительность PostgreSQL и переход на Redis

## 1. Цель исследования 
NFR 1000 RPS

Текущая реализация PostgreSQL блокировкой: `SELECT FOR UPDATE NOWAIT`.

**Цель:** Замерить производительность и время деградации БД при множественном конкурентном доступе к одной строке билета, чтобы подтвердить или опровергнуть необходимость перехода на in-memory кэш (Redis).

---

## 2. Методология
- **Инструмент:** k6 (сценарий `race_condition`)
- **Условия:** 100 и 1000 виртуальных пользователей (VU) одновременно отправляют `POST /api/bookings/lock`, пытаясь забронировать один и тот же `seatId`.
- **Метрика:** `booking_lock_duration_ms` — чистое время отклика эндпоинта, выполняющего транзакционную блокировку в базе.
---

## 3. Результаты замеров

### Сценарий А: Смешанная нагрузка (Без жесткого Race Condition)
При равномерной нагрузке, когда юзеры бронируют *разные* билеты, PostgreSQL справляется без проблем:
- **Медианное время ответа:** ~17 мс
- **Среднее время:** ~30 мс
*База работает в штатном режиме, транзакции проходят быстро.*

### Сценарий B: Средний Race Condition (100 одновременных запросов в один билет)
Имитация небольшого старта продаж (100 юзеров жмут "купить" в одну миллисекунду).
- **Минимальное время (первый успешный лок):** 114 мс
- **Среднее время ожидания отказа:** 294 мс
- **95-й перцентиль (p95):** 417 мс
*Вывод:* Время обработки простейшего запроса вырастает в **14-20 раз**. 

### Сценарий C: Целевой Race Condition (1000 одновременных запросов)
Были выкручены лимиты Tomcat (`max-threads: 1000`) и HikariCP (`maximum-pool-size: 1000`), чтобы сервер мог принять удар.
- **Успешных запросов до БД:** 312 из 1000
- **Отброшено ОС (TCP Connection Refused):** 688 из 1000
- **Среднее время ответа БД:** 1294 мс (1.3 секунды)
- **95-й перцентиль (p95):** 3571 мс (3.5 секунды)
- **Максимальное время:** 4098 мс (4 секунды)

### Сценарий D: Контрольная попытка 1000 запросов
Вторая итерация.
- **Успешных запросов до БД:** 559 из 1000 (остальные отбились по TCP, несмотря на расширение)
- **Среднее время ответа БД:** 2390 мс (2.4 секунды)
- **95-й перцентиль (p95):** 4765 мс (4.8 секунды)
- **Максимальное время:** 4952 мс (5 секунд)
*Вывод:* Чем больше транзакций база пытается обработать одновременно, тем сильнее внутренний оверхед СУБД. Увеличение вычислительных пулов (горизонтальное масштабирование веб-сервера) не помогает, наоборот усугубляет блокировки внутри базы.

---

## 4. Анализ "узких мест" (Почему так происходит?)

1. **Row-Level Lock Contention (MVCC):** 
   Тратятся огромные ресурсы на управление в postgres.
2. **Исчерпание пула коннектов (HikariCP):** 
   Транзакция висит по 3.5 секунды. При 1000 RPS пулы моментально исчерпываются.
3. **Отказ TCP-стека и Каскадное падение (Cascading Failure):**
   Потоки Tomcat зависают в ожидании БД -> очередь Tomcat (`accept-count`) переполняется -> ОС (Windows/Linux) начинает агрессивно отбивать новые TCP-сокеты (`Connection refused`). В итоге ложится весь сервис.

---

## 5. Обоснование перехода на Redis (SETNX)

Для достижения целевых показателей в 1000 RPS и защиты системы от каскадных падений нужно вынести механизм распределенной блокировки (Distributed Lock) в in-memory кэш.

**Преимущества Redis в данном контексте:**
- **Атомарность и Однопоточность:** Команда `SETNX` (Set if Not eXists) работает в одном потоке в оперативной памяти (RAM). Сложность операции O(1).
- **Скорость:** Redis способен обрабатывать сотни тысяч таких команд в секунду. Ожидаемое время ответа при 1000 RPS составит 2-5 мс (против 3500-15000 мс в PostgreSQL).
- **Разгрузка основной БД:** PostgreSQL будет полностью избавлен от мусорных транзакций. База будет получать только 1 финальный запрос на UPDATE от того юзера, который реально забрал лок в Редисе.
- **Защита пулов:** Потоки Tomcat будут получать быстрый отказ за 2 мс и тут же отдавать клиенту `409 Conflict`, мгновенно освобождая HTTP-поток для новых запросов.

---

## 6. Итоговые результаты (После миграции на Redis)

### Сценарий E: Redis + Оптимизация валидации
Механизм `SETNX` был внедрен, а проверка пользователя перенесена *после* захвата кэша. Увеличены лимиты Tomcat (`accept-count=2000`, `max-connections=10000`).
- **Успешных запросов до БД:** Ровно 1 (Победитель)
- **Отброшено ОС:** Зависит только от мощности балансировщика, сама архитектура способна принять все 1000.
- **Среднее время ответа (для проигравших):** 144 мс (падение в ~15 раз по сравнению с БД)
- **95-й перцентиль (p95):** 366 мс
- **Максимальное время:** 377 мс
*Вывод:* База данных полностью защищена от лавины конкурирующих транзакций. Redis успешно отсеивает 999 "лузеров" за доли секунды, полностью подтверждая гипотезу. NFR 1000 RPS успешно достигнут на уровне приложения.

## 9. Сводное сравнение: PostgreSQL NOWAIT vs Redis SETNX

> Все цифры — после JVM warmup (исключён Run 1). Условия: 1000 VU, shared-iterations, один и тот же seatId, localhost.

### 9.1 Latency (после прогрева, pool=1000)

| Метрика | PG NOWAIT | Redis SETNX | Разница |
|---------|-----------|-------------|---------|
| avg | 450–670 мс | 235–350 мс | **~2x лучше** |
| median | 405–680 мс | 266–372 мс | **~2x лучше** |
| p95 | 780–1210 мс | 328–578 мс | **~2x лучше** |
| max | 820–1270 мс | 389–610 мс | **~2x лучше** |

> Абсолютные значения отражают localhost (Windows TCP стек + loopback). В продакшне с балансировщиком абсолютные цифры будут ниже, но **соотношение сохранится**.

---

### 9.2 Нагрузка на PostgreSQL

| | PG NOWAIT | Redis SETNX |
|-|-----------|-------------|
| Транзакций в PG при 1000 VU | ~300–500 конкурирующих | **ровно 1** |
| `FOR UPDATE NOWAIT` конфликтов | сотни | 0 |
| Риск исчерпания HikariCP pool | высокий | отсутствует |
| Риск каскадного падения | подтверждён (Сц. C/D) | **устранён** |

---

### 9.3 Влияние размера Connection Pool (PG NOWAIT)

| Pool | Run 2 avg | Run 2 p95 | Run 4–5 avg |
|------|-----------|-----------|-------------|
| pool=20 | 1170 мс | 2170 мс | ~490 мс |
| pool=1000 | 670 мс | 1210 мс | ~470 мс |

При Redis SETNX размер пула **не имеет значения** — до PG доходит 1 запрос.

---

### 9.4 Итоговый вывод

| Критерий | PG NOWAIT | Redis SETNX |
|----------|-----------|-------------|
| Latency avg (после warmup) | 450–670 мс | **235–350 мс** |
| Предсказуемость (max) | 800–1270 мс | **390–610 мс** |
| Транзакций в БД | ~350 | **1** |
| Защита от cascading failure | нет | да |
| Поведение при Redis-аутаже | — | graceful degradation → PG |

**Основной результат:** Redis SETNX снижает latency в **~2 раза** и полностью исключает конкурентную нагрузку на PostgreSQL.
Архитектура устойчива к отказу Redis: при его недоступности система автоматически деградирует на PG NOWAIT.
